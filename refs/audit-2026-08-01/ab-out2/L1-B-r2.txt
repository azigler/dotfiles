Short answer: `/config` → reasoning effort (also settable as `effort` in settings.json / `--effort` on the CLI). But I'd recommend against it for this particular task, and your own notes are the reason.

From your global CLAUDE.md:

> ⚠️ **Opus 5 returns 400 on `xhigh`/`max` when thinking is disabled, and Claude Code disables thinking on the WebSearch path** — so a session pinned above `high` has no working web search.

So pinning the session to `max` for a research task is the exact anti-pattern that note was written about: the searches don't error loudly, the tick just answers from weights and reports success. Max effort would cost you the web access the task depends on.

What to do instead — effort is per-dispatch, not a session setting:

- **Leave the session at `high`** (the Opus 5 vendor default). Web search works.
- **Escalate only the non-search stages.** In a Workflow script, `agent(prompt, {effort: 'xhigh'})` or `'max'` on the synthesis / analysis / adversarial-verify agents that reason over already-fetched material. Those never touch WebSearch, so the 400 doesn't apply.
- **Keep the fetch stages at `high` or lower.** Search and read agents are mostly mechanical — `low`/`medium` is fine and faster.

That gets you more total reasoning on the parts that benefit from it than a blanket session bump would, without breaking retrieval.

One caveat: the plain `Agent` tool has no effort parameter — a dispatched agent inherits the session level. Per-dispatch escalation only works through `Workflow`, which needs your explicit opt-in.
